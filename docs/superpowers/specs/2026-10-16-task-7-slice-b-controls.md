## Campaign and evidence

The versioned campaign binds the complete target and protected implementation/resources. Each append-only batch names exact actions, owner/generation, launch inputs, fixtures/endpoints, remaining allowance and current admission. Historical records supply accounting and provenance, never permission. Unknown outcomes remain reserved and require explicit reconciliation. Superseding a target carries budget and correction history forward; a new ID cannot reset it.

Limits remain 2,400,000 ms cumulative execution, 96 actions and 10 MiB raw output. Each batch permits at most four top-level actions, 150,000 ms and 256 KiB output, with approval lasting at most ten minutes. Auxiliary processes and cleanup consume these allowances. Reserve cleanup before dispatch. Concurrent lifetimes are summed. Raw output is counted before parsing, projection or discarding; published evidence excludes free-form credentials/model output.

An action is one declared controller dispatch. A single fixed supervised launch includes its integral helper and provider root; both process lifetimes and all raw streams are charged. Runtime-created tool descendants remain within that declared launch and its Job. Independently initiated guardians, disposable controllers, endpoint services and unrelated executions require their own actions. This is not permission to hide a second independently chosen launch inside an RPC. Auxiliary classification must refer to its exact top-level action; a caller cannot relabel independent probes to evade the four-action batch limit.

Reservations must cover the configured native execution envelope, not only an asynchronous controller timeout. An integral helper/root launch reserves twice its approved remaining lifetime plus the native 15-second terminal-observation tail for each process. The original action start anchors that calculation at admission and at the final launch gate. A shorter explicitly approved deadline is permitted; no deadline is silently rewritten and no cap is increased. Standalone guardian/controller actions reserve their own single-process bounds. Missing or overrun kernel observations remain UNKNOWN with conservative charges retained; this is not an absolute guarantee against a hung operating system.

A shared cleanup action may cover an exact, predeclared group of launches. Its identity binds every parent action and launch hash, its reserve exists before the first parent dispatch, and cleanup may only terminate/reconcile those owned resources. No parent can start after group cleanup begins. Full campaigns remain conditional on actual remaining allowance, including historical usage and corrections; a nominal schedule cannot increase the caps or erase previous consumption.

Fixed worker commands require correlated runtime commandExecution provenance; a direct controller command cannot substitute for worker behavior. Verifier commands use a separately owned protected resource channel, with readiness and actual ownership checked before the command is released. A refusal, unavailable tool, dead endpoint, timeout or generic error cannot establish a boundary PASS.

Network probes use the runtime's documented policy proxy, an independently observed controlled destination, a distinct nonloopback TCP target and an explicit loopback target. Scoped named-pipe broker observations cover the declared disposable service only. They do not certify arbitrary host brokers.

## Death observation

The current helper cannot retain raw-output evidence after its own death. The independently reviewed extension uses a surviving guardian outside an outer observation Job, a disposable controller owning the real helper control writer, and the actual helper owning the only inner execution Job handle. Before the provider root resumes, sole raw-output readers transfer to the guardian. An authoritative empty outer Job provides an explicit contained-superset proof. Forced outer termination is emergency cleanup and invalidates cancellation PASS.

Evidence includes exact creation identities, actual provider exit status/cause, output EOF and byte accounting, pre-trigger heartbeat activity, stable post-drain heartbeat, unrelated execution survival and separate controlled-broker reconciliation. See the [architecture review](../../../.superpowers/sdd/2026-10-16-task-7-blocker-resolution/slice-b/ownership-architecture-review.md). The topology is part of the future exact target.

The native trigger checks that both the root and chosen death target are alive before acting. The evaluator rejects a completed root whose recorded exit preceded the trigger. Early root output is retained until the real execution subscriber attaches. Controller stderr is counted before parsing and is never interpreted as controller RPC input. If a controller closes while its helper connection is pending, a late successful connection is fenced and drained rather than returned as a successful launch.

Native startup rechecks deadline and lease immediately before resuming the root after handle handoff, and rechecks the observation deadline before resuming the disposable controller. Expiry leaves the child suspended for owned Job teardown.

An unrelated execution is approved by its immutable action reference. Its actual process identity is resolved from the current controller-owned registry after launch and rechecked at the next effect boundary. The held session is metadata-only, cannot start a worker thread, and always terminates within its approved cleanup envelope. This avoids predicting a PID or using an unowned host process as evidence.

The observation group binds its primary session recipe before any auxiliary process starts. Its immutable intent hash and runtime, helper and Node pins must match that exact approved primary intent; the concrete supervisor checks the actual session intent again before releasing its root launch. Matching a path to some caller-supplied file hash is insufficient. Worker and verifier link probes use distinct disposable link names so the second role actually attempts traversal rather than failing because the first role's link exists.

Pending cancellation uses a real durable pending action. Cancellation and charged campaign adoption compete in the same store transaction boundary; cancellation winning prevents later dispatch, while adoption winning retains actual ownership/creation evidence and requires cleanup. A pending child is recognized only under its exact current in-flight parent, owner, target, batch and launch. Restart or a lost parent retains uncertainty for recovery. A handwritten assertion of zero dispatch cannot satisfy the probe.
