# Startup closure evidence, rule startup-closure-v1

This matrix describes the production reducer in `src/qualification/startup-evidence.ts`. It is an evidence contract, not acceptance of the current runtime. No live qualification was executed by this implementation task.

The qualified scope is **headless local stdio, new thread**. Thread resume, reload, desktop clients and remote clients are explicit exclusions. A future scope or relevant target change requires fresh source coverage, observation and independent acceptance.

| Decision | Required evidence |
| --- | --- |
| Plugins | Reviewed plugin and plugin-contribution routes for all eight source classes at bootstrap and thread start; compatible actual policy and complete owned runtime observation. |
| Browser/computer | Reviewed native browser, external/CDP browser and computer routes, including concrete source-backed inapplicability for this headless client; compatible actual policy and owned observation. Desktop inventory is not claimed. |
| MCP | Reviewed ordinary, managed/cloud and plugin MCP contribution routes at both admitted boundaries; effective restriction or valid effective-registration monitoring. No complete remote inventory is claimed. |
| Managed requirements | Compatible observed effective config, requirements, permission profile, launch environment and shell environment policy; reviewed source precedence; controlled fault injections through the production `checkControls` consumer; actual allowed work plus denied source-write, sensitive-read and network probes for worker and independent verifier. |
| Strict config | Two separate dispatched actions with the same validated baseline, positive initialization and natural exit zero, negative exact `foo` classification with nonzero natural exit and zero RPCs, both completely drained. |

Remote control, hooks/legacy notify, apps/web and environment are independently evaluated supporting requirements. Five closed blocker records alone do not make the overall target qualified.

Every surface route names applicable packaged, system, managed, user, project, session, cloud and plugin sources. The reviewed route names the pinned commit, complete stored source bytes, consumer and lifecycle, plus its enforcement classification. A persistent restriction or headless inapplicability must be justified by those concrete sources and the actual observed policy. A registered canary additionally needs exact registration and monitor hashes, an effective registration artifact tied to the action intent, a prelaunch baseline, post-drain observation and zero attributable activations. A controller-written `MONITOR_CHECK` supplies none of that registration attribution.

The coverage manifest and exact observation artifacts require an independent review artifact. The controller explicitly pins the accepted review digest; discovering a review-shaped file, a reviewer UUID or a successful model response does not establish trust. The reviewer must verify the stated source semantics. Hash verification establishes byte identity, not the truth of a source interpretation.

`loadStartupEvidence` checks stored artifact metadata and complete bytes, exact full target, campaign, batch, owner generation, approved action, dispatch, operation result, successful owned cleanup and absence of pending/unknown evidence. The pure reducer accepts only an opaque bundle produced by that loader. It rechecks history and artifact bytes when evaluating; copied bundles, changed targets, missing or simulated proof, wrong action links, changed source bytes and later unresolved failures stay open. Historic decisions are not reusable execution authority.

`createManagedPolicyConflictEvidence` is a pure production diagnostic. It projects observed runtime config and requirements, requires the ordinary compatible baseline, injects disallowed ChatGPT login and disallowed approval-policy requirements, and invokes the same `checkControls` function used at the real admission boundary. Its result remains `fault_injection`. Publish that safe result under an already owned diagnostic action and bind it to the compatible LIVE policy proof. This does not modify managed/cloud policy or supply LIVE boundary evidence.

Existing backend policy proof is emitted only when actual config exposes both the selected permission-profile hash and shell environment policy hash. The launch environment digest is separately checked against the actual launch environment. Missing optional fields keep dependent claims open. Existing inactivity fixtures without effective registration provenance remain diagnostic evidence.

Development verification: the startup evidence suite passed 14 cases against synthetic temporary-store artifacts; session-driver and ledger suites passed 73 cases. These prove implementation behavior, not actual provider, host boundary, startup inactivity or managed policy qualification. A source-backed coverage package, compatible LIVE observations, controlled conflict artifact, strict pair, real role-specific boundary evidence and independent acceptance remain required for actual closure.
