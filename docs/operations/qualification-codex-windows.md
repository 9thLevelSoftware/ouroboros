## Historical implementation notes

The notes below record earlier ledger/preflight stages and prepared commands. They are not the current campaign runbook or evidence of current qualification. In particular, a replaced named permission profile does not imply that app-server accepts a root `--profile` flag; use the supported form in the corrected plan. Do not invoke these examples as live permission. Earlier stage-specific test counts are retained, not newly rerun.

Ordinary `ouroboros doctor [--json]` uses its existing informational dependencies. It never calls the qualifier, creates fixtures, writes qualification records, or makes model requests. The explicit qualification dispatch is:

```powershell
npm run dev -- doctor --qualify --provider codex --environment windows --fixture-root <fresh-absolute-disposable-root> --model <configured-model> --effort high
```

This command currently prints the concrete manifest, prepares fresh disposable fixtures, and persists an unqualified report. It exits 1 while startup authority remains unproven. It does **not** start the provider or verifier. Invalid/duplicate arguments and existing or overlapping fixture roots are rejected. No global configuration, login, service, credential, or host ACL changes are performed. Controller records remain outside the worker-writable workspace. Preserve incomplete fixture/controller records for review after a preflight error.

Each target binds the pinned native Codex executable/version/hash, adapter source identity, helper executable/version/hash, verifier executable and wrapper identity, Node executable/version/hash, OS identity, complete requested policy/configuration, and model/effort. Changing any bound input requires new qualification; version strings and profile names alone confer no support. A passing cached receipt never authorizes a current dispatch.

Approval records bind the complete target and manifest hashes, exact disposable roots, controlled endpoint targets, approved probe IDs, finite attempt/time/output budgets, current owner nonce/generation, and action identity. The store appends bounded records to its existing `qualifications` table under an immediate transaction, owner/action fence and expected-history revision. It never updates or erases prior qualification records. Actions are durably intended before dispatch; a crash or unknown action requires reconciliation and is never automatically replayed.

The ledger records `PASS`, `FAIL`, and `UNTESTED` independently for every worker and verifier probe. An unexecuted operation or model refusal is `UNTESTED`. Denial requires a trusted controller observation of a real blocked operation, intact evidence bytes and preserved sentinel hashes. Sensitive reads must expose no marker bytes. Cancellation requires the exact owned root/helper identity, actual root exit, empty Job membership, complete output, a stable nonempty heartbeat for two seconds, and survival of an unrelated process. Provider inventory remains explicitly incomplete; Job drain does not manufacture a complete provider inventory.

Fixtures and injected responses are separate evidence classes. Fixture passes cannot qualify live subscription, filesystem, network, tool-loading or cancellation behavior. Injected auth/quota responses cover structured stop/checkpoint behavior only; they do not prove subscription success. A first failed attempt establishes the problem; at most two corrective candidates follow, and reopening the ledger preserves their ordinals. Passing probes cannot be rerun without a separately authorized narrow revalidation path.
